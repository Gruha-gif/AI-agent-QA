# Skill «test-design»

## Purpose - Назначение

строить тестовую модель для Qase по требованиям, которые прошли проверку качества  
skill описывает, что именно нужно проверить, и включает позитивные, негативные и граничные сценарии, но не запускает тесты и не создаёт записи в Qase

## When to Use - Когда применяется

после того как агент проверил качество анализа требований  
skill запускается параллельно с task-design и опирается на те же проверенные требования  
если требования изменились, тестовую модель нужно пересмотреть

## Inputs - Входные данные

агент передаёт skill:

- проверенные требования с номерами вида REQ-001, критериями приёмки и ссылками на источник  
- границы тестирования - какая функциональность и платформы рассматриваются  
- правила проекта Qase: код проекта, структура наборов тестов, обязательные поля и соглашения по оформлению  
- правила приоритета, если заказчик их задал  
- номер текущей версии требований  
- место сохранения результата и режим работы

skill не ходит в Qase самостоятельно и не создаёт там записи  
всё, что ему нужно для работы, передаёт агент

## Procedure - Порядок работы

1. проверить входные данные и убедиться, что требования прошли проверку качества  
2. определить объекты проверки, роли, состояния, входные данные и риски по требованиям  
3. для каждого требования решить, применимы ли позитивная, негативная и граничная проверки  
4. если тип проверки неприменим, записать причину, а не придумывать сценарий ради количества  
5. выбрать технику для каждой группы проверок: классы эквивалентности, граничные значения, таблицы решений или переходы состояний, и указать основание выбора  
6. для числового диапазона проверить значения ниже минимума, минимум, чуть выше минимума, чуть ниже максимума, максимум и выше максимума, убрав повторы  
7. если граница или шаг не указаны в требованиях, сформулировать вопрос, а не придумывать значение  
8. для каждой проверки подготовить номер вида TEST-001, название, ссылки на требования, тип, технику, предусловия, данные, шаги, ожидаемый результат для каждого шага, приоритет и набор тестов  
9. ожидаемые результаты брать только из требований, а текст сообщений об ошибках указывать дословно лишь тогда, когда он есть в источнике  
10. составить матрицу связей требований и проверок, проверить дубликаты и перепроверить полноту и воспроизводимость  
11. сохранить результат как артефакт

## Rules - Правила

- не придумывать поведение системы, которого нет в требованиях  
- не придумывать границы, классы данных и текст сообщений об ошибках  
- не выдавать предположения за ожидаемый результат  
- не генерировать сценарии ради количества и не дублировать проверки  
- обосновывать каждый случай, когда тип проверки признан неприменимым  
- не запускать тесты и не отмечать их как пройденные - skill только проектирует проверки  
- не создавать и не удалять сценарии в Qase - это делает агент в разрешённом режиме  
- не использовать задачи Jira как источник бизнес-правил вместо требований  
- не публиковать результат без разрешения  
- не хранить в описании skill данные конкретного проекта: код проекта, адреса, имена людей - всё это приходит из входных данных  
- не скрывать пробелы в покрытии и открытые вопросы

## Output - Результат

оформленная тестовая модель, сохранённая как отдельный результат работы, в нём есть:

- **наборы тестов** - как проверки разложены по структуре проекта Qase  
- **список проверок** - номер, название, ссылки на требования, тип, техника, предусловия, данные, шаги, ожидаемые результаты, приоритет и набор тестов  
- **применимость** - какие типы проверок применимы к каждому требованию, а какие нет, и почему  
- **матрица покрытия** - какие требования покрыты проверками, а какие нет и почему  
- **открытые вопросы** - чего не хватает в требованиях для построения точных проверок  
- **готовность** - можно ли передавать модель дальше или работа заблокирована, и почему

у результата должен быть статус: черновик, проверен, заблокирован, с ошибкой или устарел

## Completion Criteria - Критерии завершения

skill выполнен, когда:

- каждое требование покрыто проверкой либо обосновано, почему проверка не нужна  
- для каждого применимого типа проверки есть хотя бы один сценарий  
- шаги воспроизводимы, а данные указаны конкретно  
- ожидаемые результаты однозначны и подтверждены требованиями  
- матрица покрытия составлена, дубликаты проверены  
- открытые вопросы записаны  
- результат перепроверен и сохранён с корректным статусом

решение о том, можно ли передавать модель в Qase и переходить к следующему этапу, принимает агент после проверки качества
